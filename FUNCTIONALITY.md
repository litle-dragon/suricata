# Опис функціоналу репозиторію (за кодом)

Документ описує, що реально роблять скрипти цього репозиторію, на основі
прочитаного коду (не README-маркетингу). Система: Suricata (IDS) читає копію
WAN-трафіку через MikroTik, alert-bridge.py реагує на алерти — блокує
атакуючих на MikroTik і шле дайджести в Telegram. Решта скриптів — допоміжні
(аналітика, міграція, парсинг правил, синхронізація).

---

## 1. `alert-bridge.py` — головний демон (systemd service, `main()` у нескінченному циклі)

### Що робить
Читає `eve.json` Suricata в режимі `tail -F` (переживає logrotate), для
кожного алерту з severity ≤ 2 приймає рішення блокувати/не блокувати на
MikroTik і накопичує статистику в SQLite + Telegram-дайджести.

### Алгоритм читання логу — `follow(path)`
Кастомний tail-ف: відкриває файл, запам'ятовує inode і позицію (`pos`).
На кожній ітерації:
- якщо файл змінив inode АБО зменшився в розмірі (`st.st_size < pos`) —
  файл перевідкривається (обробка logrotate/truncate);
- якщо новий рядок є — yield;
- якщо немає — виконує `check_periodic_tasks()` (таймерні події) і `sleep(0.5)`.
Якщо файл ще не існує — `sleep(1)` і повтор (`FileNotFoundError`).

### Класифікація напрямку трафіку — `classify_flow(ev)`
Порівнює `src_ip`/`dest_ip` з `HOME_NETS` (RFC1918 + CGNAT + власні WAN
IP/IPv6-префікси з `.env`):
- src не в HOME, dest в HOME → **inbound** (ззовні атакують LAN);
- src в HOME, dest не в HOME → **outbound** (LAN атакує/стукає назовні);
- обидва або жоден — inbound, якщо src не HOME, інакше outbound (fallback).
Повертає `(direction, target_ip, internal_ip)`, де `target_ip` — той бік,
що НЕ є домашнім (тобто атакуючий або зовнішня ціль).

### Вайтлист — `whitelisted(ip)`
IP з `WHITELIST` (RFC1918/CGNAT/loopback, публічні DNS-резолвери Cloudflare/
Google/Quad9/OpenDNS/AdGuard, власні WAN-адреси) ніколи не блокується і не
рахується. Захист від блокування власного DNS-резолвера.

### Підмережева агрегація — `get_subnet(ip)`
IPv4 → `/24`, IPv6 → `/64`. Вся статистика і поріг блокування рахуються не
тільки по окремих IP, а й по підмережах — типовий прийом проти ботнетів, де
атака йде з пулу сусідніх адрес.

### Облік хітів і рішення про поріг — `record_hit(direction, ip, sig)`
Для inbound:
1. Перевіряє IP і підмережу проти all-time множин `_all_time_seen_ips` /
   `_all_time_seen_subnets` (кеш з таблиць SQLite, завантажений при старті) —
   визначає "нову" IP/підмережу (ще ніколи не бачену за всю історію).
2. Пише/оновлює рядок у `seen_ips` / `seen_subnets` (SQLite, `INSERT OR IGNORE`
   для нових, інакше `UPDATE ... total_hits+1`).
3. Інкрементує лічильники слоту (6 год) і доби (для дайджестів і порогів).
4. Повертає `(ip_daily_count, subnet_str, subnet_daily_unique_count)`.
Для outbound — просто рахує лічильник за добу, без all-time трекінгу.

### Логіка блокування (у `main()`, гілка inbound)
- **Ескалація за кількістю спроб**: 1–2 спроби за добу → тимчасовий блок
  (`BLOCK_TIMEOUT`, дефолт 1h). На 3-й спробі (`PERMANENT_THRESHOLD = 3`) —
  **постійний** блок на MikroTik (`permanent=True`), понад 3 — ігнор
  (вважається вже заблокованим).
- **Cooldown** (`cooled_down`, `COOLDOWN = 300s`): для тимчасових блоків не
  дублює REST-виклик для того самого `ip+signature_id` частіше ніж раз на
  5 хв (захист від nmap-скану, який засипає роутер однаковими запитами).
  Постійний блок cooldown НЕ чекає — блокується одразу.
- **Агрегація підмереж**: якщо кількість унікальних IP у /24 за добу досягає
  `SUBNET_THRESHOLD = 10`, весь /24 блокується **постійно** одним викликом
  (`mikrotik_block(subnet_str, ..., permanent=True)`), незалежно від стану
  окремих IP.
- Для **outbound** — завжди тимчасовий блок (1h), без ескалації, без
  постійного блоку, без cooldown-виключень.

### Anomaly / Spike detection — ковзне вікно
`_sliding_window_alerts` — список подій за останні `SLIDING_WINDOW = 300s`
(5 хв), поповнюється при кожному inbound-алерті. `check_spike(now)`:
- обрізає застарілі записи (старші 5 хв) з голови списку;
- якщо `len(window) >= SPIKE_THRESHOLD_N` (дефолт 500) І з моменту останнього
  спайк-алерту минуло ≥ `SPIKE_COOLDOWN = 900s` (15 хв) → надсилає
  `send_spike_alert()` і пише подію в `spike_events`.
Це єдина подія, яка пейджить у реальному часі — все інше йде дайджестами.

### Часові тригери — `check_periodic_tasks()`
Викликається на кожній ітерації `follow()` (навіть коли нових рядків немає):
1. **6-годинний слот** (`00-06/06-12/12-18/18-24`, `_slot_index = hour // 6`):
   при переході в новий слот — `send_6h_slot_digest()` для щойно завершеного
   слоту, потім `_reset_slot_state()`.
2. **Північ** (зміна `today` рядка дати): `snapshot_daily_stats()` записує
   повний денний зріз у `daily_stats`, потім `_reset_daily_state()`.
3. **07:00 ранку**: якщо звіт за сьогодні ще не надсилався —
   `send_7am_daily_report()`, який читає вчорашній рядок з `daily_stats`
   (а не рахує наліту — тому не залежить від пам'яті процесу).
При старті процесу після 07:00 звіт за "вчора" примусово не шлеться повторно
(`_last_7am_report_date` виставляється одразу в сьогоднішню дату) — захист
від спаму при рестартах сервісу.

### Формат дайджестів — `_top_and_singles`, `_format_top_lines`
Зі словника `{subnet: {"ips": set, "alerts": int}}` будує:
- топ-10 підмереж з ≥2 IP, сортування за (alerts, ips) спадно, з середнім
  алертів/IP;
- окремо рахує "одиночні" IP (підмережі з 1 IP, тобто не агреговані) —
  кількість і сумарні алерти.
Усі середні округлюються до цілого (`round()`), по вимозі спеки.

### Інтеграція з MikroTik REST API — `mikrotik_block(ip_or_subnet, sig, permanent)`
- `PUT /rest/{ip|ipv6}/firewall/address-list` — додає адресу у список
  `suricata-block` з коментарем (обрізаним до 60 символів, префікс
  `"PERMANENT: "` для постійних).
- Тимчасовий блок — з полем `timeout=BLOCK_TIMEOUT`.
- Перед постійним блоком спочатку **шукає і видаляє** динамічний (з
  timeout) запис для тієї ж адреси через `GET` + `DELETE` — щоб постійний
  запис не конфліктував/дублювався з тимчасовим.
- `verify=False` (самопідписаний сертифікат роутера), `auth=(MT_USER,
  MT_PASS)` — Basic Auth.
- Успіх — HTTP 200/201 або текст відповіді містить "already" (вже в списку).

### Telegram — `telegram_send(text)`
Просто `POST` у Bot API `sendMessage`; якщо `TG_TOKEN`/`TG_CHAT` не задані —
тихо виходить (блокування працює без сповіщень). Підтримує форум-тред
(`message_thread_id`).

### Персистентність — SQLite (WAL mode)
`_conn = sqlite3.connect(..., isolation_level=None)` — autocommit,
`PRAGMA journal_mode=WAL` + `synchronous=NORMAL` — компроміс швидкість/
надійність при можливому крешу. П'ять таблиць: `seen_ips`, `seen_subnets`
(all-time унікальність), `daily_stats` (архів по днях), `slot_digests`
(архів 6-годинних дайджестів), `spike_events` (лог аномалій).

## 2. `analyze_stats.py` — CLI-аналітика поверх SQLite (read-only)

Читає ту саму базу в режимі `mode=ro` (`sqlite3.connect("file:...?mode=ro")`)
— гарантія, що аналітика не може випадково зіпсувати робочу базу демона.

- `--sum` (дефолт): таблиця по днях з `daily_stats` + підсумкові суми.
- `--day YYYY-MM-DD`: повний розбір одного дня (усі поля + топ підмереж).
- `--spikes`: історія всіх spike_events.
- `--top N`: топ-N підмереж (агреговано з `seen_ips` через
  `aggregate_seen_subnets`) і топ-N окремих IP за `total_hits`.
- `--sync-mikrotik [--min-ips N]`: бере all-time підмережі з ≥N (дефолт 10)
  унікальних IP і **постійно** блокує їх на MikroTik (`sync_subnets_to_mikrotik`):
  1. підтягує креденшели з `/opt/alert-bridge/env` (`load_env`);
  2. для кожної підмережі — знаходить і видаляє окремі IP-записи в
     block-листі, які вже покриваються цією підмережею (дедуплікація), потім
     видаляє динамічний запис самої підмережі якщо є;
  3. додає постійний запис підмережі з коментарем "PERMANENT SUBNET (N IPs,
     M hits)".
Це другий, "batch"-шлях блокування підмереж — на відміну від live-порогу
в alert-bridge.py (10 IP **за добу**), тут поріг — 10 IP **за всю історію**.

## 3. `migrate_json_to_sqlite.py` — одноразова міграція легасі-стану

До переходу на SQLite бридж зберігав стан у двох JSON-файлах
(`alert-bridge-total-state.json` — накопичувальний, `alert-bridge-state.json`
— поточний день). Скрипт:
1. Читає обидва файли (`inbound_counts: {ip: count}`), мерджить через `max()`
   на IP (кумулятивний файл домінує, денний доповнює пропуски).
2. З кожного IP виводить підмережу (`get_subnet`, та сама логіка /24-/64) і
   сумує хіти по підмережах.
3. `INSERT OR IGNORE` в `seen_ips`/`seen_subnets` — ідемпотентно, ніколи не
   перезаписує існуючі рядки, безпечно запускати повторно чи на живій базі.
Мета: щоб перший день після переходу не показав усіх вже відомих атакуючих
як "нових". Only inbound — точно дзеркалить, що рахує сам бридж для
all-time унікальності.

## 4. `parse_rules_ips.py` — витяг репутаційних IP/підмереж з правил Suricata

Не пов'язаний напряму з alert-bridge (окрема утиліта для формування списку
блокування на MikroTik з вмісту самих сигнатур).

### Алгоритм
1. Regex `^\s*alert\s+\w+\s+\[([^\]]+)\]` — знаходить рядки правил виду
   `alert <proto> [ip1,ip2,...] ...` і витягує вміст квадратних дужок.
2. Другий regex витягує з цього вмісту токени, схожі на IP/CIDR (IPv4/IPv6 з
   опційним `/prefix`), знімає провідний `!` (заперечення в Suricata-синтаксі).
3. `aggregate_ips_to_24(items, min_ips_per_24=2)`:
   - готові підмережі (prefix < 32/128) лишаються як є;
   - окремі IP групуються за батьківським /24 (або /64 для IPv6);
   - якщо в /24 потрапило ≥ `min_ips_per_24` адрес — уся /24 йде в результат
     замість окремих IP (стиснення списку);
   - інакше окремі IP лишаються окремими записами;
   - фінальний прохід прибирає одиночні IP, які вже покриті якоюсь підмережею
     з результату (уникнення дублікатів).
Результат — сортований список підмереж/IP, або в stdout, або у файл
(`--output`), який потім споживає `sync_rules_to_mikrotik.py`.

## 5. `sync-state-from-journal.py` — легасі-відновлення JSON-стану з journalctl

Позначено в README як "unused since SQLite migration" — залишений код,
описує, як раніше відновлювався стан після втрати `alert-bridge-state.json`.

### Алгоритм
1. `journalctl -u alert-bridge --since today` — витягує лог-рядки поточного
   сервісу за сьогодні.
2. Двома regex парсить `attacker=<ip>` (inbound) і `target=<ip>` (outbound) з
   рядків формату, який писав старий `alert-bridge.py` у stdout/journal.
3. Фільтрує IP через `is_home_or_lan` (той самий набір RFC1918/CGNAT/DNS-
   резолверів, продубльований локально в цьому файлі, а не імпортований).
4. Мерджить лічильники з існуючим `alert-bridge-state.json` (якщо дата
   збігається) через `max()`, інакше починає новий стан на сьогодні.
5. Атомарний запис: пише у `.tmp`, потім `os.replace()` — уникнення
   пошкодження файлу при обриві процесу.

## 6. `sync_rules_to_mikrotik.py` — масове завантаження списку блоку на MikroTik

Приймає файл, вироблений `parse_rules_ips.py` (`malicious_subnets.txt`), і
заливає його на роутер одним REST-викликом через `/rest/execute` (виконання
RouterOS-скрипту), а не через окремі POST/PUT на кожен запис.

### Алгоритм
1. `load_malicious_items` — читає файл, унікалізує, сортує.
2. `deduplicate_subnets_and_ips` — прибирає окремі /32 (/128) IP, які вже
   покриті якоюсь підмережею зі списку (та сама ідея, що й у
   `parse_rules_ips.py`, але без агрегації — тільки дедуплікація готового
   набору).
3. `sync_via_rest_execute`:
   - ділить список на чанки по `chunk_size` (дефолт 400) — обхід лімітів на
     розмір payload/довжину RouterOS-скрипту;
   - перший чанк починається з `/ip firewall address-list remove [find
     list=<name>]` — повне очищення старого списку перед заливкою нового;
   - кожен елемент чанку — рядок `add list=<name> address=<net>
     comment="ET Rule Subnet"`;
   - весь чанк відправляється одним `POST /rest/execute` з тілом
     `{"script": "<текст RouterOS-скрипту>"}` — це вибір "Option A: пряме
     виконання без запису файлів на диск роутера" (уникнення проблем з
     правами на файлову систему MikroTik).
Немає інтеграції з `seen_ips`/`seen_subnets` SQLite — джерело даних тут
виключно текстовий файл від `parse_rules_ips.py`, тобто цей ланцюжок
незалежний від живого бриджа й БД.

## Загальна архітектура даних (як усе пов'язано)

```
eve.json (Suricata) → alert-bridge.py (демон) → SQLite alert_bridge.db
                                              → MikroTik REST (live-блок)
                                              → Telegram (спайк/6h/07:00)

alert_bridge.db → analyze_stats.py (звіти, --sync-mikrotik: all-time поріг)

suricata.rules → parse_rules_ips.py → malicious_subnets.txt
                                    → sync_rules_to_mikrotik.py → MikroTik REST
                                       (окремий, batch-шлях, не залежить від БД)

legacy JSON (*.json) → migrate_json_to_sqlite.py → seen_ips/seen_subnets (one-time)
journalctl logs → sync-state-from-journal.py → legacy JSON (unused, залишок)
```

Два незалежні механізми постійного блокування підмереж:
1. **Live, поріг за добу**: `alert-bridge.py`, 10 унікальних IP в /24 **за
   один день** → миттєвий постійний блок.
2. **Batch, поріг за всю історію**: `analyze_stats.py --sync-mikrotik`, 10
   унікальних IP в /24 **за весь час** (дефолт, змінюється `--min-ips`) →
   ручний/за розкладом запуск.

## Ключові алгоритмічні прийоми, використані наскрізь
- **Ковзне вікно (sliding window)** — anomaly detection без зберігання
  повної історії, O(1) амортизовано на вставку/очистку.
- **Фіксовані часові слоти замість rolling** — 6-годинні дайджести прив'язані
  до годинника (00/06/12/18), а не "кожні 6 годин з моменту старту" —
  передбачувані часи сповіщень.
- **All-time множини в пам'яті + SQLite як backing store** — швидка перевірка
  "чи бачили цю IP колись" без запиту до диска на кожен алерт.
- **Ескалація за лічильником спроб** (1-2 тимчасово, 3+ постійно) — типовий
  паттерн graduated response, зменшує false positive на разові збіги.
- **Агрегація по /24 (/64)** — виявлення розподілених атак з одного пулу
  адрес, які поодинці не перетнули б поріг.
- **Cooldown per (ip, signature)** — rate limiting на дії, а не на дані,
  захист зовнішнього API (MikroTik REST) від сплеску викликів.
- **WAL-режим SQLite** — конкурентний запис (демон) + читання (analyze_stats.py)
  без блокування один одного.
- **Chunked REST execute** — обхід лімітів розміру запиту при масовому
  імпорті правил на мережевий пристрій.
